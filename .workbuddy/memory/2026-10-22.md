## 秒传与存储去重架构讲解 · 面试准备

用户针对简历条目"流式增量 MD5 秒传 + 内容寻址去重 + 引用计数，10 用户复用 100 MiB 节省 90% 存储"要求结合代码细致讲解。已通读并讲透全链路：

- 核心是 CAS（内容寻址存储）：file_info（物理内容，uq_md5）→ user_file_list（关联，UNIQUE(user,md5,file_name)）→ user_file_count（配额，UNIQUE(user)）；count=关联行数即引用计数。
- 指纹：前端 SparkMD5 2MiB 分片（picture_bed/src/services/images.js:36），服务端 common/md5.c + chunk_store.c:173 chunk_hash_file / :189 chunk_verify（按序喂同一 ctx，发布前全量校验）。
- 秒传入口 src_cgi/md5_cgi.c → content_reuse（content_store.c:129）= GET_LOCK + content_bind + RELEASE_LOCK；返回码 0/1/2，md5_cgi 翻译为对外的 0/5/1。
- content_bind（content_store.c:68）七步事务：ON DUPLICATE no-op 保赢家行权威、SELECT FOR UPDATE 锁行、竞争输家同事务 content_queue_gc 入队（outbox）、1062 幂等锚点、两个 count=count+1 原子自增。
- 发布在 chunk_merge_cgi.c：merge 前先 bind(id=NULL) 预检（上传期间被别人发布的退化为立刻绑定）；merge_storage 用 journal（appender 文件存 FDFS file_id，mkstemp+fsync+rename）+ 远程长度为权威追加游标 + 非整片边界截断。
- 删除 content_detach（content_store.c:141）：指纹锁+行锁内断链，count 归零才入队 GC + 删 file_info 行；tools/storage_gc.c 删前复查 file_info 引用（live check），失败 attempts+1 重试。
- 三层并发防护分工：uq_md5 兜底正确性、FOR UPDATE 护已存在行计数、GET_LOCK 覆盖"行不存在"窗口（首次发布无行可锁）且连接断开自动释放，故不用 Redis 锁。
- 已知边界（讲解时主动坦白）：90% 只算内容字节不含元数据/备份/副本；秒传路径信任客户端 MD5 无法服务端验证；多实例需共享文件系统（flock/本地目录语义）；Appender 创建到 journal 持久化之间有孤儿窗口。
